How the Supervisor fits into the CN application

A plain-language walk through the whole flow, from "something happened to a borrower" to "one agent contacted them, and we can prove why". No prior knowledge assumed.

1. The problem in one minute

CN is moving from one bot to several agents, each doing a different job with borrowers (people who owe money):

  • Reminder: "your payment is due soon"
  • Negotiation: "can we agree a new payment plan?"
  • Servicing: "here is your statement / update your details"
  • Legal: formal notices

Each agent works alone. So on the same day, Reminder might text a borrower "pay now" while Negotiation offers them a discount. That is confusing, may break rules, and afterwards nobody can say why it happened.

The Supervisor's job is to sit in the middle and make sure that, for every borrower:
  1. only one agent is "in charge" at a time (the active owner),
  2. nobody gets contacted twice in conflicting ways on the same day,
  3. if an agent crashes, loops forever, or returns garbage, we recover without losing anything and without double-contacting,
  4. every decision is written down with its reason, so an auditor can replay any account.

The Supervisor does not write messages itself. The agents' own logic is out of scope. The Supervisor is a traffic controller.

2. What is an "event bus"? (the term you asked about)

Start with the plain idea: something happens, and the system needs to be told. Examples of "things that happen":

Payment received (account 17) Due date is tomorrow (account 42) Borrower broke a promise to pay (account 8) Legal flag set (account 99) Agent crashed (account 42)

Each of those is called an event: a small record saying "this happened, to this account, at this time".

An event bus is just a shared mailbox for events.
Whoever notices something drops an event into the mailbox. The Supervisor takes events out, one by one, in order, and deals with them. The sender does not need to know who will handle it, and the handler does not need to know who sent it.

Why not just call the supervisor directly?

Without a mailbox

The payment system calls the supervisor directly. If the supervisor is busy or restarting, the call is lost. And if five systems call at once for the same borrower, you get chaos.

With a mailbox

Events wait safely in line. If the supervisor restarts, the events are still there. Events for one borrower are handled one at a time, in order. That alone prevents many "two agents at once" problems.

"Partitioned by account": what that means

Imagine one lane per borrower. Events for borrower 42 always go through lane 42, so they can never be processed at the same moment by two workers. Different borrowers use different lanes, so thousands can be processed in parallel. That is all "partition by account_id" means.

What would the bus actually be at CN?

The problem statement lists "event bus" as a tool the supervisor must call but does not name a technology. The concept is what matters; the implementation can be any of these:

OptionWhat it isWhen it fits
A database table event_queueRows with status PENDING / DONESimplest. Fine for 20,000 accounts. What I'd start with.
A queue service (SQS, RabbitMQ)Managed mailboxIf CN already runs one
KafkaHigh-volume log of eventsOnly if CN already has it; overkill otherwise

Decision for you: does CN already have a queue or event system? If yes, we plug into it. If no, we use a database table. The supervisor logic is identical either way.

4. Step-by-step flow (one event, from start to finish)

Take one event: "Due date is tomorrow for account 42." Here is everything that happens.

0

Something happens trigger

A scheduler runs every morning and notices account 42 is due tomorrow. (Other triggers: a payment arrives, a collector clicks a button in the CN app, an agent reports it finished.)

1

An event is dropped on the bus event bus

The scheduler writes: {"type": "DUE_SOON", "account_id": 42, "time": "2026-11-19 09:00"} into the mailbox, in lane 42. It then forgets about it. It does not wait for an answer.

2

The Supervisor picks it up consume

The Supervisor takes the next event for account 42. While it works on account 42, nothing else touches account 42. LangGraph opens a "thread" named 42, which is that account's own saved notebook.

3

Load what we know about the borrower state

Read from your existing tables (days past due, legal flag, any open promise to pay) plus the Supervisor's own record (who currently owns this borrower, when they were last contacted). All of it goes into one Python dictionary called the state. This is the first node in our prototype.

4

Guardrails: is it even allowed? safety

Plain yes/no checks, no AI involved:

  • Is another agent already the active owner? Then this event waits.
  • Was the borrower already contacted today? Then do not contact again.
  • Has this borrower or this agent used up its budget (max contacts)? Then stop.

If any check fails, we write "blocked, because ..." to the trace and stop here.

5

Route: choose exactly one agent decision

Fixed rules, checked in order, first match wins. For example:

legal flag set          -> Legal
payment received        -> Servicing
promise to pay broken   -> Negotiation
days past due 30-90     -> Negotiation
otherwise               -> Reminder

The answer plus the reason ("DPD 5 is 30 or below") is stored in the state. Rules are used because they are instant: the requirement is under 100 ms.

6

Take ownership, then call the agent act

The Supervisor marks "Reminder owns account 42 right now", then calls the Reminder agent. Because the owner is now recorded, no other agent can start on account 42.

7

Check what the agent returned validate

Did it return the expected shape (status, outcome)? If it returned nonsense, that is a "malformed output" fault and we go to the recovery path (section 5).

8

Record the contact, safely idempotent

Before the message goes out, the Supervisor writes a contact-log row with a unique key like 42 | 2026-11-19 | reminder. If the system crashes and replays this step, the key already exists, so the message is not sent a second time. This is how we guarantee zero double contacts.

9

Update state and release ownership commit

Save "last contact = now", clear the owner, close the event as DONE in the bus.

10

Write the reason into the trace audit

One line per decision: what the event was, which agent, why, and the result. Because every node of the graph is also checkpointed, an auditor can open account 42 and replay the whole day.

5. When something breaks

The test day injects faults on purpose. Each has a simple response:

FaultWhat it looks likeWhat the Supervisor does
Crash before sendingAgent dies, nothing was sentSafe to retry: run the agent again
Crash after sendingAgent dies, but the borrower already got the messageContact log shows it was sent, so mark it done. Never resend.
LoopAgent keeps saying "in progress" foreverAfter 3 tries, stop it and hand the borrower to another agent or to a human
Malformed outputAgent returns garbageRetry once; if it happens again, reroute
Two events at onceTwo agents want the same borrowerThe owner lock lets one in; the other waits or is dropped, with the reason logged
Never seen beforeSomething the rules did not anticipateAn LLM may suggest one action from a short safe list (retry, skip, reroute, quarantine). The rules still have the final say.
Supervisor itself restartsProcess killed mid-runLangGraph checkpoints let it resume at the exact node it stopped at
The "Monitor" is a watcher that checks agent health (is it alive, is it making progress). It can only read and request a recovery. Only the Supervisor changes the state. This keeps one single writer and avoids a second source of conflicts.
Where the LLM is used, and where it is not: it is not in the 100 ms routing path. It is only called for the rare unscripted fault, and it can only pick from a fixed safe menu. That is what makes the system agentic without becoming unpredictable.

6. How this shows up on your account / customer listing page

(Proposal: I have not seen the CN front end, so adjust to match your real pages.)

  • Listing page: shows, per account, who currently owns it, when it was last contacted, and status. The data comes straight from the Supervisor's borrower_state table, joined to your existing account data.
  • Detail page: a "journey trace" tab. The auditor picks an account and sees every event, decision, reason and agent result in time order. This is what judges will ask for.
  • A manual action (collector clicks "contact now") does not call an agent directly. It posts an event, and the Supervisor applies the same guardrails. A human cannot accidentally cause a double contact either.
The Supervisor is a background service, not code that runs when a page loads. The page only reads the results and drops requests onto the bus.

7. Where LangGraph and the checkpointer fit

  • Graph: the steps in section 4 are the nodes of one LangGraph graph. Edges decide what runs next (for example, guardrail fails -> stop; agent output bad -> recovery).
  • State: one dictionary (TypedDict) that flows through the graph. Each node returns only the pieces it changes, and LangGraph merges them.
  • Thread: one thread per borrower: thread_id = account_id. That gives every account its own private saved history.
  • Checkpointer: after every node, LangGraph saves the state to a database. If the process dies between node 6 and node 8, on restart it reloads the last saved state and continues from the exact next node. That is the "survives restart without losing state" requirement.
  • Stub agents inside the graph: in the prototype each stub agent is a node. In production they may be separate services reached through a small adapter, but the supervisor graph looks the same.

Two kinds of memory, do not confuse them:

CheckpointOur own tables (borrower_state, contact_log)
What it remembersWhere the graph was mid-runBusiness facts about the borrower
LifetimePer run, per accountPermanent
Used forResume after a crash, replayLocks, daily cap, audit, listing page

How we build the prototype (the order you asked for)

  1. Step 1 (done): one node, load_borrower, plus a checkpointer. See the state fill in and reload it from disk.
  2. Step 2: add route (rules pick an agent, reason stored).
  3. Step 3: add the stub agent nodes (reminder, negotiation).
  4. Step 4: add commit with the contact log and the one-contact-per-day rule.
  5. Step 5: add the fault injector and the recovery path (crash, loop, bad output).
  6. Step 6: add the monitor and the LLM for unscripted faults.

After each step we run it and print the state before and after, exactly as in step 1.

TermPlain meaning

Open questions for you

  1. Does CN already have a queue or event system, or should we use a database table?
  2. Which database does the app use (Postgres, MySQL, other)? That decides where the Supervisor tables and checkpoints live.
  3. Do the real agents expose a heartbeat or a "message sent" confirmation? The crash-after-send logic depends on it.
  4. Are there consent flags or contact limits in the data beyond D1, D2, D4 and D6? They are not in what we were given.
