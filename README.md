# MT-02 Multi-agent journey supervisor

```
backend/Orchestrator/   the supervisor (LangGraph + SQLite) and the dashboard API   -> http://localhost:8001
frontend/               the React dashboard (Vite + MUI)                              -> http://localhost:5173
```

## Run it

One command (starts both, Ctrl+C stops both):

```bash
./run_demo.sh
```

or in two terminals:

```bash
cd backend/Orchestrator && .venv/bin/python -m scripts.serve_ui      # API + the live monitor + the demo walkthrough
cd frontend && npm run dev                                           # then open http://localhost:5173
```

The first start loads the dataset into two databases (`data/live` for the real side, `data/demo` for the walkthrough), so it takes
longer; later starts reopen them and keep everything. Older single-database modes remain: `--mode day` (a simulated day on a clock,
press play) and `--mode scenario` (walkthrough only).

## How it works

**Two separate databases.** The *Workflow walkthrough* on the Overview (15 demo events, Run button, graph animation) runs on its own
database. It explains the workings and can be reset at any time; it never touches the numbers, runs, alerts or accounts.

**The live monitor.** A background worker that runs whenever the server runs (not tied to anyone being logged in). It watches a fixed
pool of 15 real borrowers. Inside the contact window (the policy's hard window, rule R007, 08:00-19:00; override with
`MT02_MONITOR_WINDOW=08:00-17:00`) it appends events as they fall due and runs them. Outside the window it does nothing; events
already waiting are handled when the window opens. The pool and each borrower's next-due time are stored, so a restart picks up where
it stopped. Pause or resume it from the header. Settings: `MT02_MONITOR_EVERY_MIN` (minutes between events per borrower, default 30),
`MT02_MONITOR_TICK_S` (default 3). Events are generated by a schedule here; a real event feed would call an `POST /api/events` endpoint
(not built yet).

**Notifications.** When a real run hits an agent fault and the supervisor recovers it, an alert drops in at the top:
*"Alert Supervisor Agent - WhatsApp agent/Crash happened and recovering"* with **Mark as read** and **Ignore**. Ignoring closes the
alert but leaves it unread. The bell shows the number of unread alerts; clicking it opens a small panel listing them (each with
**Mark as read** and **View run**). Marking read removes it from the panel and the count. Read state is saved in the database.

**Navigation.** *Journey Supervisor*: Overview, Journey Runs (every finished real run, with fault and recovery), Decision Log.
*Loan Management*: Accounts.

## Where the data comes from

Everything on screen is read from the SQLite database the supervisor writes (`backend/Orchestrator/data/ui/orchestrator.db`),
through a second read-only connection. Nothing is mocked: the same LangGraph runs, the same rows are written.

| Page | What it shows | Tables |
|---|---|---|
| Overview | six headline tiles (real runs only), then the demo walkthrough: event picker, live graph, phone preview, step log | `event_queue`, `decision_log`, `contact_log` (live); `demo_event`, `run_step` (demo) |
| Journey Runs | one row per finished real run: borrower, event, channel, owner after, outcome, fault and recovery, duration | `journey_run` |
| Decision Log | every decision with its reason and the D12 rule ids; filters live in the URL | `event_queue`, `decision_log` |
| Accounts | all 20,000 accounts, server-side filter / sort / paging, live owner and last contact; a row opens the borrower trace | `ds_account`, `ds_person`, `contact_log`, `ds_history` |

API reference: see the docstring at the top of `backend/Orchestrator/orchestrator/ui/app.py`.

## Things to know

* **Personal data.** Names and phone numbers are stored only masked (`D*** S***`, `XXXXXX4842`); emails and addresses are not stored.
  All data is synthetic. A test asserts that no real name, phone or email from the source files ever leaves the API.
* **Time.** Times are simulated wall-clock times sent as ISO strings ending in `Z`, so the browser shows exactly what the supervisor saw.
* **Total O/S and Installment Overdue** are not in the source data (D1); they are left empty and hidden rather than invented.
* **Account status** is derived from D1 flags: legal, restructured, settled (settlement flag), overdue (DPD > 0), current.
* The channel agents are stubs: nothing is ever sent.
