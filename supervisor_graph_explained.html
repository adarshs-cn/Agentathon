The Supervisor Graph, node by node

1. GraphState vs BorrowerState

In one sentence each.
BorrowerState is the borrower's permanent file: who owns them, when they were last contacted, what they promised.
GraphState is the clipboard the supervisor carries while handling one event: the event, a copy of the file, the decision, the agent's result, any fault.

The most important rule: only three nodes (assign, commit, release) write to the borrower's file, and agents never do. Everything else only reads it or changes the clipboard. That keeps one trustworthy record per borrower.

A subtlety worth knowing. The checkpointer saves GraphState under thread_id = account_id. So when the same account gets a second event, LangGraph starts with the previous run's final GraphState still in place. That is why the first node, validate_event, resets the scratch fields. Scenario 2 in the dry runs shows it.

2. The other stores

Besides BorrowerState there are three more durable things the nodes read or write. In this prototype they are in-memory Python objects; in production they are tables.

StoreRow shapeWho writesWhy it exists
contact_log{key, account_id, agent, time}
key = B1|2026-11-20|reminder		the send() function, called by an agentThe truth about what was actually sent. The monitor reads it after a crash. A repeated key is refused, so a replay cannot double-send. Daily caps and agent budgets are counted from it.
decision_log{event_id, account_id, node, text}every node, one line eachThe audit trail: what each node decided and why. This is what "a complete trace for any account" is built from.
events_done{event_id: status}close_eventMarks an event finished, so it is never processed twice.

Agent budgets are not a separate table: they are counted from contact_log, so there is no second number that could drift out of step.

4. Every node

Each card says what the node does in plain words, what it reads, what it writes (split into GraphState and the durable stores), and where it goes next. The real code is under each card.

validate_event supervisor node

Gatekeeper and reset

Two jobs. First, clear the scratch fields left over from this account's previous event, because LangGraph keeps one saved state per account and we do not want yesterday's fault leaking into today's run. Second, check the event is well-formed and the account exists. A bad event is rejected here and the run ends cleanly.

Readsevent; the account list
Writes to GraphStateguard, decision, attempt, result, fault, sent, recovery, outcome (all reset); outcome if rejected
Writes to storesdecision_log
Goes next toload_borrower, or close_event if rejected
Show the real code
def validate_event(state: GraphState) -> dict:
    ev = state["event"]
    reset = {"guard": None, "decision": None, "attempt": 0, "result": None,
             "fault": None, "sent": False, "recovery": None, "outcome": None}
    missing = [k for k in ("id", "type", "account_id", "time") if not ev.get(k)]
    if missing:
        why = f"event is missing {missing}"
    elif ev["type"] not in KNOWN_EVENTS:
        why = f"unknown event type {ev['type']}"
    elif ev["account_id"] not in STORE.profile:
        why = f"unknown account {ev['account_id']}"
    else:
        log(state, "validate_event", "event is well-formed, scratch fields reset")
        return reset
    log(state, "validate_event", f"REJECTED: {why}")
    return {**reset, "outcome": {"status": "REJECTED", "reason": why}}

def load_borrower(state: GraphState) -> dict:
    acc = state["event"]["account_id"]
    rec = STORE.borrower_state[acc]
    b = {"account_id": acc, **STORE.profile[acc],
         "owner": rec["owner"], "last_contact": rec["last_contact"],
         "commitments": list(rec["commitments"]), "status": rec["status"]}
    log(state, "load_borrower", f"loaded {acc}: dpd={b['dpd']} owner={b['owner']} status={b['status']}")
    return {"borrower": b}

guardrails supervisor node

Hard yes/no safety checks

No AI, only rules, checked in this order: (1) is the borrower paused (status not ACTIVE)? (2) is another agent already the owner? (3) was the borrower already contacted today? If any fails, the run is blocked and a reason is recorded. This is where 'zero conflicting contacts' is enforced.

Writes to GraphStateguard; outcome if blocked
Writes to storesdecision_log
Goes next toroute, or close_event if blocked

def guardrails(state: GraphState) -> dict:
    b, ev = state["borrower"], state["event"]
    date = ev["time"][:10]
    if b["status"] != "ACTIVE":
        g = {"ok": False, "rule": "STATUS", "reason": f"borrower is {b['status']}, automation paused"}
    elif b["owner"]:
        g = {"ok": False, "rule": "OWNER_LOCK", "reason": f"{b['owner']} is already the active owner"}
    elif len(contacts_today(b["account_id"], date)) >= PER_BORROWER_CAP:
        g = {"ok": False, "rule": "DAILY_CAP", "reason": "already contacted today (1/1)"}
    else:
        g = {"ok": True, "rule": "NONE", "reason": "no owner, not contacted today, status ACTIVE"}
    log(state, "guardrails", ("ALLOWED: " if g["ok"] else "BLOCKED: ") + g["reason"])
    out = {"guard": g}
    if not g["ok"]:
        out["outcome"] = {"status": "BLOCKED", "reason": g["reason"]}
    return out

route supervisor node

Pick exactly one agent

Fixed rules, first match wins: legal flag, payment received, promise broken, open promise (nobody), DPD 90+, DPD 30 to 89, otherwise Reminder. It also checks the chosen agent's daily budget. The agent and the reason are stored. It is pure rules so it takes microseconds, well inside the 100 ms limit.

Writes to GraphStatedecision; outcome if no agent
Writes to storesdecision_log
Goes next toassign, or close_event if no agent

def route(state: GraphState) -> dict:
    b, ev = state["borrower"], state["event"]
    date = ev["time"][:10]
    if b["legal_flag"]:
        agent, why, rule = "legal", "legal flag is set", 1
    elif ev["type"] == "PAYMENT_RECEIVED":
        agent, why, rule = "servicing", "payment received", 2
    elif ev["type"] == "PTP_BROKEN":
        agent, why, rule = "negotiation", "promise to pay was broken", 3
    elif b["commitments"]:
        agent, why, rule = None, f"open promise to pay ({b['commitments'][0]['due']}), do not contact", 4
    elif b["dpd"] >= 90:
        agent, why, rule = "legal", f"DPD {b['dpd']} is 90 or more", 5
    elif b["dpd"] >= 30:
        agent, why, rule = "negotiation", f"DPD {b['dpd']} is between 30 and 89", 6
    else:
        agent, why, rule = "reminder", f"DPD {b['dpd']} is below 30", 7
    if agent and agent_count(agent, date) >= PER_AGENT_CAP:
        agent, why, rule = None, f"{agent} agent daily budget used up", 8
    log(state, "route", f"rule {rule}: {agent or 'NO AGENT'} because {why}")
    out = {"decision": {"agent": agent, "reason": why, "rule": rule}}
    if agent is None:
        out["outcome"] = {"status": "SUPPRESSED", "reason": why}
    return out

assign supervisor node

Take the owner lock

Writes the chosen agent as the borrower's owner in the durable table before the agent is called. From now until release, nobody else can act on this borrower. Also resets the attempt counter to 0.

def assign(state: GraphState) -> dict:
    acc, agent = state["borrower"]["account_id"], state["decision"]["agent"]
    STORE.borrower_state[acc]["owner"] = agent                  # take the lock (durable)
    log(state, "assign", f"owner lock taken: {agent} owns {acc}")
    return {"borrower": {**state["borrower"], "owner": agent}, "attempt": 0}

agents stub agent node

The four stub agents: reminder, negotiation, servicing, legal

Four nodes built from one factory, one per stub agent. Each calls its stub, handing it a send() function that writes the contact_log row and then delivers. The stub may raise an exception (crash, timeout) or return something odd (garbage, 'in progress'). A LangGraph node that raises would abort the whole run, so the node catches the exception and stores it in the state as fault. Which fault happens is decided by the fault injector, which the supervisor knows nothing about.

def make_agent_node(name):
    def agent_node(state: GraphState) -> dict:
        ev, acc = state["event"], state["borrower"]["account_id"]
        attempt = state.get("attempt", 0) + 1
        try:
            out = AGENT_OBJS[name].run(acc, send=make_send(acc, name, ev))
            log(state, name, f"attempt {attempt}: agent returned {out}")
            return {"attempt": attempt, "result": out, "fault": None}
        except AgentCrash as e:
            log(state, name, f"attempt {attempt}: agent CRASHED ({e})")
            return {"attempt": attempt, "result": None, "fault": {"type": "CRASH", "detail": str(e)}}
        except AgentTimeout as e:
            log(state, name, f"attempt {attempt}: agent TIMED OUT ({e})")
            return {"attempt": attempt, "result": None, "fault": {"type": "TIMEOUT", "detail": str(e)}}
    agent_node.__name__ = name
    return agent_node

    def run(self, acc, send):
        fault = self.injector.next_fault(acc)
        if fault == "CRASH_BEFORE_SEND": raise AgentCrash("agent died before sending")
        if fault == "TIMEOUT":           raise AgentTimeout("agent never answered")
        if fault == "MALFORMED":         return {"oops": "garbage"}
        if fault == "LOOP":              return {"account_id": acc, "status": "IN_PROGRESS"}
        send(acc)
        if fault == "CRASH_AFTER_SEND":  raise AgentCrash("agent died after sending")
        return {"account_id": acc, "status": "DONE", "outcome": "CONTACTED"}

validate_output supervisor node

Check what the agent returned

If the agent node already reported an exception, it keeps that fault. Otherwise it checks the shape: 'IN_PROGRESS' means NO_PROGRESS (possible loop), missing fields or a status other than DONE means MALFORMED. A good result clears the fault. When the agent already reported an exception it returns nothing, which is why such steps show 'no change'.

Writes to storesdecision_log

def validate_output(state: GraphState) -> dict:
    if state.get("fault"):                       # agent node already reported an exception
        log(state, "validate_output", f"fault already reported: {state['fault']['type']}")
        return {}
    res = state.get("result")
    keys = set(res) if isinstance(res, dict) else set()
    if isinstance(res, dict) and res.get("status") == "IN_PROGRESS":
        f = {"type": "NO_PROGRESS", "detail": f"still IN_PROGRESS after attempt {state['attempt']}"}
    elif not REQUIRED_OUTPUT <= keys or res.get("status") != "DONE":
        f = {"type": "MALFORMED", "detail": f"got keys {sorted(keys)}, expected {sorted(REQUIRED_OUTPUT)}"}
    else:
        log(state, "validate_output", "output has the right shape")
        return {"fault": None}
    log(state, "validate_output", f"FAULT {f['type']}: {f['detail']}")
    return {"fault": f}

monitor fault handling

Diagnose the fault

The key move is that it asks the contact_log, not the agent, whether a message went out. Sent already: skip (never resend). Not sent: retry while the attempt limit allows, then reroute. A fault with no rule (such as TIMEOUT) falls to the catch-all, which quarantines. In the full design that last branch consults the LLM, which may only choose from a safe menu. It is not wired in here.

def monitor(state: GraphState) -> dict:
    ev, acc = state["event"], state["borrower"]["account_id"]
    fault, n = state["fault"], state["attempt"]
    sent = len(contacts_today(acc, ev["time"][:10])) > 0         # ask the contact_log, not the agent
    t = fault["type"]
    if sent:
        action = "RESTART_SKIP_CURRENT"
        why = f"{t}, but contact_log already has today's send: do not call the agent again"
    elif t == "CRASH":
        action, why = ("RESUME", "crash before anything was sent: safe to retry") if n < MAX_RETRIES_OTHER \
            else ("REROUTE", "crashed again: stop retrying")
    elif t == "MALFORMED":
        action, why = ("RESUME", "bad output, nothing sent: retry once") if n < MAX_RETRIES_OTHER \
            else ("REROUTE", "second bad output: stop retrying")
    elif t == "NO_PROGRESS":
        action, why = ("RESUME", f"no progress yet (attempt {n} of {MAX_ATTEMPTS})") if n < MAX_ATTEMPTS \
            else ("REROUTE", f"no progress after {n} attempts: this is a loop")
    else:                                                          # catch-all: unscripted fault
        action, why = "QUARANTINE", f"unscripted fault {t}: no rule, hold borrower for human review"
    log(state, "monitor", f"{t} -> {action}: {why}")
    return {"sent": sent, "recovery": {"action": action, "reason": why}}

recover fault handling

Apply the recovery

Carries out what the monitor decided. RESUME clears the fault and the graph jumps back to the same agent node, not to the start, so guardrails and routing are not repeated. SKIP builds a DONE result from the already-logged send. REROUTE or QUARANTINE builds an ESCALATED result. It never writes to the event bus.

Writes to GraphStatefault (cleared), result (for skip and escalate)

def recover(state: GraphState) -> dict:
    acc, action = state["borrower"]["account_id"], state["recovery"]["action"]
    if action == "RESUME":
        log(state, "recover", "RESUME: go back to the same agent node")
        return {"fault": None}
    if action == "RESTART_SKIP_CURRENT":
        log(state, "recover", "SKIP: treat the already-logged send as the result")
        return {"fault": None, "result": {"account_id": acc, "status": "DONE",
                                          "outcome": "CONTACTED", "via": "recovery"}}
    log(state, "recover", f"{action}: give up on automation for this borrower")
    return {"fault": None, "result": {"account_id": acc, "status": "ESCALATED", "outcome": action}}

commit supervisor node

Write the result to the borrower's file

For a successful contact it records last_contact. For an escalation it sets the status to NEEDS_REVIEW or QUARANTINED and records no contact. This is one of only three nodes that write to the borrower's file.

def commit(state: GraphState) -> dict:
    acc, ev, res = state["borrower"]["account_id"], state["event"], state["result"]
    b = dict(state["borrower"])
    if res["status"] == "DONE":
        b["last_contact"] = ev["time"]
        log(state, "commit", f"contact recorded, last_contact={ev['time']}")
    else:
        b["status"] = "NEEDS_REVIEW" if res["outcome"] == "REROUTE" else "QUARANTINED"
        log(state, "commit", f"no contact; status set to {b['status']}")
    STORE.borrower_state[acc].update(last_contact=b["last_contact"], status=b["status"])
    return {"borrower": b}

def close_event(state: GraphState) -> dict:
    ev = state["event"]
    out = state.get("outcome")
    if not out:
        res = state["result"]
        out = {"status": "CONTACTED" if res["status"] == "DONE" else "ESCALATED",
               "agent": state["decision"]["agent"], "attempts": state["attempt"]}
    STORE.events_done[ev["id"]] = out["status"]
    log(state, "close_event", f"event {ev['id']} closed as {out['status']}")
    return {"outcome": out}

7. What is simplified here, and what is assumed

  • The graph handles one event. A small driver loop takes the next event off the bus and calls graph.invoke / stream with thread_id = account_id. The bus is not a node.
  • Events run one after another. So the owner lock cannot be seen blocking a truly simultaneous event; scenario 10 pre-sets an owner to show the check. In production the lock must be an atomic compare-and-set in the database.
  • The LLM is not wired in. The monitor's catch-all branch quarantines. That branch is where a model would choose from a fixed safe menu (resume, skip, reroute, quarantine), never overriding the guardrails.
  • Policy choices I made, for you to confirm: at most 1 contact per borrower per day (so even a payment-confirmation after a reminder is blocked), 10 per agent per day, the DPD thresholds 30 and 90, the rule order in route, and that an open promise to pay suppresses all contact.
  • Commitments are seeded by hand (B9). In production they would come from your data or from promise-to-pay events.
  • Time is taken from the event, which also keeps replays deterministic.
  • The fault injector is ours. It runs from a plain dict script inside the stub agents. The real judging harness may deliver faults differently; the supervisor only ever reacts to what it observes (an exception, a bad return, silence).
  • Persistence: checkpoints use SQLite here (in memory for this report). Production would use Postgres.
